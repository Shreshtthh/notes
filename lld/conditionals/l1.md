Lesson 1

Strategy Pattern — Replace Behavior Conditionals with Polymorphism
TL;DR: Use Strategy when the branches contain different ways to perform the same action. Put each behavior behind a common interface and let the caller delegate to it. If the branches only call constructors and return an object, that responsibility is Factory, not Strategy.

Warning — Don't Force Patterns: Pattern count is not a quality metric. Use Strategy when interchangeable behavior is a real boundary; keep a local conditional when it is clearer. Several named patterns may legitimately appear in a larger design, and one unnecessary abstraction can already be too much.

The Pain: One Conditional Owns Several Volatile Behaviors
Here is a payment processor that handles multiple payment methods:

// BAD: every new payment type means modifying this class
class PaymentProcessor {
    public boolean processPayment(String type, long amountInCents) {
        if (type.equals("credit_card")) {
            // validate card number
            // charge via card gateway
            System.out.println("Charging credit card: " + amountInCents + " cents");
            return true;
        } else if (type.equals("paypal")) {
            // authenticate with PayPal
            // send payment request
            System.out.println("Sending PayPal payment: " + amountInCents + " cents");
            return true;
        } else if (type.equals("crypto")) {
            // convert to crypto amount
            // submit blockchain transaction
            System.out.println("Submitting crypto payment for quoted fiat amount");
            return true;
        }
        throw new IllegalArgumentException("Unknown payment type: " + type);
    }
}
Now the business says "add Apple Pay." You open PaymentProcessor and add another branch. Then bank transfer and gift cards arrive. Each change touches the same dispatch method and mixes channel-specific dependencies in one class. That is evidence for a behavior boundary when payment channels change independently.

The conditional is not wrong merely because it is a conditional. The problem is that the chosen extension axis—payment channel—keeps changing while the processor owns every channel's implementation. Strategy can localize those behavior changes, though composition or registration code may still change when a new implementation is installed.

The Cure: Strategy Pattern
Define an interface for the behavior that varies. Each payment type becomes its own class implementing that interface. The caller holds a reference to the interface and delegates to it.

Java
C++
Python
Copy
// The strategy interface
interface PaymentStrategy {
    boolean process(long amountInCents);
}

// Each payment type is a separate class
class CreditCardPayment implements PaymentStrategy {
    private final String paymentToken;

    public CreditCardPayment(String paymentToken) {
        if (paymentToken == null || paymentToken.isBlank()) {
            throw new IllegalArgumentException("paymentToken");
        }
        this.paymentToken = paymentToken;
    }

    @Override
    public boolean process(long amountInCents) {
        if (amountInCents <= 0) throw new IllegalArgumentException("amount");
        // Charge through a gateway using the token; never log raw card credentials.
        return true;
    }
}

class PayPalPayment implements PaymentStrategy {
    private final String accountToken;

    public PayPalPayment(String accountToken) {
        if (accountToken == null || accountToken.isBlank()) {
            throw new IllegalArgumentException("accountToken");
        }
        this.accountToken = accountToken;
    }

    @Override
    public boolean process(long amountInCents) {
        if (amountInCents <= 0) throw new IllegalArgumentException("amount");
        // Send through the provider using the account token.
        return true;
    }
}

class CryptoPayment implements PaymentStrategy {
    private final String walletAddress;

    public CryptoPayment(String walletAddress) {
        if (walletAddress == null || walletAddress.isBlank()) {
            throw new IllegalArgumentException("walletAddress");
        }
        this.walletAddress = walletAddress;
    }

    @Override
    public boolean process(long amountInCents) {
        if (amountInCents <= 0) throw new IllegalArgumentException("amount");
        // convert to crypto, submit blockchain transaction
        return true;
    }
}
The cart can receive a strategy for each checkout. Passing it as an argument avoids a half-configured cart whose strategy is still null:

class ShoppingCart {
    private final List<Item> items = new ArrayList<>();

    public void addItem(Item item) {
        items.add(Objects.requireNonNull(item));
    }

    public boolean checkout(PaymentStrategy strategy) {
        Objects.requireNonNull(strategy);
        long totalInCents = items.stream()
            .mapToLong(Item::getPriceInCents)
            .reduce(0L, Math::addExact);
        if (totalInCents <= 0) throw new IllegalStateException("Cart is empty");
        return strategy.process(totalInCents);
    }
}

// Usage: choose behavior at the call site.
ShoppingCart cart = new ShoppingCart();
cart.addItem(new Item("Laptop", 99_999));

cart.checkout(new CreditCardPayment("tok_card_123"));
The snippets use integer minor units to avoid binary floating-point currency errors. A complete money type would also carry currency and specify overflow and rounding behavior; the C++ sum above is intentionally abbreviated and would need checked addition for untrusted or unbounded totals.

Adding Apple Pay can be localized to an ApplePayPayment implementation plus whichever composition/registration code makes it selectable. Existing cart behavior need not change, but its tests should still run; abstraction does not guarantee regressions are impossible.

Strategy selects behavior through composition. The implementation may be chosen per call, injected once at construction, or selected by surrounding composition code.

When NOT to Use Strategy
Strategy is not always the right call. A small, cohesive branch over a closed enum can be clearer than several one-method classes.

Java
Copy
// A closed inverse operation has one stable rule; Strategy adds no useful boundary.
Direction opposite(Direction direction) {
    return switch (direction) {
        case NORTH -> Direction.SOUTH;
        case SOUTH -> Direction.NORTH;
        case EAST  -> Direction.WEST;
        case WEST  -> Direction.EAST;
    };
}
Ask whether the branches have different dependencies, sizable algorithms, independent tests/change rates, or runtime selection needs. If they encode one compact exhaustive rule, keep the conditional. A country-tax table would be a poor “fixed” example because rates and jurisdictions change.

In an interview, "support multiple types" is only a clue. Ask what changes across those types. If the payment flow, pricing formula, or routing algorithm changes, consider Strategy. If only object construction changes, consider Factory. If the set is small and fixed, do not force either pattern.

Strategy vs Factory: They Solve Different Problems
They can look similar because both often use an interface and several implementations. Do not classify them by that shared structure. Look at the responsibility of the code:

Question	Factory	Strategy
What decision does it own?	Which object should I create?	Which behavior or algorithm should I use?
What do the branches do?	Call constructors and return an object	Perform different versions of an action
What does the caller receive?	An object behind a common interface	The result of delegated behavior
Payment example	Create CreditCardPayment or UpiPayment	Run the card or UPI payment flow
Here is the quickest way to tell them apart:

Java
Copy
// STRATEGY SMELL: the branches do the business work
if (type.equals("card")) {
    chargeCard(amount);
} else if (type.equals("upi")) {
    chargeUpi(amount);
}

// FACTORY RESPONSIBILITY: the branches only create the worker
if (type.equals("card")) {
    return new CreditCardPayment();
} else if (type.equals("upi")) {
    return new UpiPayment();
}

Java
Copy
class PaymentStrategyFactory {
    public static PaymentStrategy create(String type, Map<String, String> config) {
        return switch (type) {
            case "credit_card" -> new CreditCardPayment(required(config, "paymentToken"));
            case "paypal" -> new PayPalPayment(required(config, "accountToken"));
            case "crypto" -> new CryptoPayment(required(config, "walletAddress"));
            default -> throw new IllegalArgumentException("Unknown type: " + type);
        };
    }

    private static String required(Map<String, String> config, String key) {
        String value = config.get(key);
        if (value == null || value.isBlank()) {
            throw new IllegalArgumentException("Missing config: " + key);
        }
        return value;
    }
}

PaymentStrategy payment = PaymentStrategyFactory.create(type, config);
payment.process(amountInCents);
The Factory is allowed to contain the type conditional because mapping input to constructors is its job. Strategy keeps the payment behavior out of that conditional.

Use this interview answer:

Object selection and creation belong to Factory. Varying business behavior belongs to Strategy.

Do not label the whole design "a Factory problem" or "a Strategy problem." Name the responsibility you are solving. One design may use both, one, or neither.

Quick Recap
Concept	What it means	Why it matters
Strategy pattern	Put interchangeable ways of performing an action behind a common interface	Business branches stop spreading across callers
Composition over inheritance	The caller holds a reference to the interface, not a subclass relationship	Strategies can be swapped at runtime
When to use	Multiple implementations perform the same action in different ways	The behavior can vary without changing the caller
When to skip	One compact rule over a closed set, with no useful substitution boundary	Avoids abstraction that adds navigation without isolating change
Strategy vs Factory	Strategy performs varying behavior; Factory selects and creates an object	They often work together but own different responsibilities
