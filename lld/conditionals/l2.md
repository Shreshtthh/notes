State Machine — When Behavior Depends on State
TL;DR: First model states, events, guards, effects, and valid transitions explicitly. A small machine may be clearest as an enum plus an exhaustive switch or transition table. Use the State object pattern when substantial behavior varies by state and separate state implementations improve ownership. Seeing the word “state” is not enough; look for the same event having different valid outcomes across lifecycle states.

class VendingMachine {
    private String state = "NO_COIN";
    private int selectedSlot = -1;

    public void insertCoin() {
        if (state.equals("NO_COIN")) {
            state = "HAS_COIN";
            System.out.println("Coin accepted");
        } else if (state.equals("HAS_COIN")) {
            System.out.println("Coin already inserted");
        } else if (state.equals("DISPENSING")) {
            System.out.println("Please wait, dispensing in progress");
        }
    }

    public void selectProduct(int slot) {
        if (state.equals("NO_COIN")) {
            System.out.println("Insert coin first");
        } else if (state.equals("HAS_COIN")) {
            selectedSlot = slot;
            state = "DISPENSING";
            System.out.println("Product selected: slot " + slot);
        } else if (state.equals("DISPENSING")) {
            System.out.println("Already dispensing");
        }
    }

    public void dispense() {
        if (state.equals("NO_COIN")) {
            System.out.println("Insert coin first");
        } else if (state.equals("HAS_COIN")) {
            System.out.println("Select a product first");
        } else if (state.equals("DISPENSING")) {
            System.out.println("Dispensing product from slot " + selectedSlot);
            selectedSlot = -1;
            state = "NO_COIN";
        }
    }
}
This particular layout contains nine state/action cases. Adding a fourth state requires deciding its behavior for all three existing actions; adding a fourth action requires a decision in all four states. That matrix exists in any complete state machine, but scattering it across methods makes omissions hard to spot.

One Implementation: State Objects
When the logic in each state is substantial, each state can be an object implementing the allowed actions. The vending machine delegates to its current state. For a three-state toy example, an enum plus an exhaustive table may be smaller; the classes below demonstrate the State pattern rather than claiming it is mandatory.

State Diagram
Before writing code, draw the state diagram. Circles are states, arrows are transitions labeled with the action that triggers them:

[NO_COIN] ---------> [HAS_COIN] -----------> [DISPENSING] -------> [NO_COIN]

This diagram is the behavioral blueprint. Each node must be represented somehow—an enum value or state object—and each transition needs an event, optional guard, effect, and next state. Transition ownership can live in state objects, the context, or a table.

// The state interface -- one method per action
interface VendingMachineState {
    void insertCoin(VendingMachine machine);
    void selectProduct(VendingMachine machine, int slot);
    void dispense(VendingMachine machine);
}

class NoCoinState implements VendingMachineState {
    @Override
    public void insertCoin(VendingMachine machine) {
        System.out.println("Coin accepted");
        machine.transitionTo(new HasCoinState());
    }

    @Override
    public void selectProduct(VendingMachine machine, int slot) {
        System.out.println("Insert coin first");
    }

    @Override
    public void dispense(VendingMachine machine) {
        System.out.println("Insert coin first");
    }
}

class HasCoinState implements VendingMachineState {
    @Override
    public void insertCoin(VendingMachine machine) {
        System.out.println("Coin already inserted");
    }

    @Override
    public void selectProduct(VendingMachine machine, int slot) {
        if (slot < 0) throw new IllegalArgumentException("slot");
        System.out.println("Product selected: slot " + slot);
        machine.selectSlot(slot);
        machine.transitionTo(new DispensingState());
    }

    @Override
    public void dispense(VendingMachine machine) {
        System.out.println("Select a product first");
    }
}

class DispensingState implements VendingMachineState {
    @Override
    public void insertCoin(VendingMachine machine) {
        System.out.println("Please wait, dispensing in progress");
    }

    @Override
    public void selectProduct(VendingMachine machine, int slot) {
        System.out.println("Already dispensing");
    }

    @Override
    public void dispense(VendingMachine machine) {
        System.out.println("Dispensing product from slot " + machine.selectedSlot());
        machine.clearSelection();
        machine.transitionTo(new NoCoinState());
    }
}

// The context -- delegates everything to the current state
class VendingMachine {
    private VendingMachineState state;
    private int selectedSlot = -1;

    public VendingMachine() {
        this.state = new NoCoinState();
    }

    public void insertCoin() { state.insertCoin(this); }
    public void selectProduct(int slot) { state.selectProduct(this, slot); }
    public void dispense() { state.dispense(this); }

    // Internal collaboration API for state implementations in this package.
    void transitionTo(VendingMachineState next) {
        this.state = Objects.requireNonNull(next);
    }
    int selectedSlot() {
        if (selectedSlot < 0) throw new IllegalStateException("No selected slot");
        return selectedSlot;
    }
    void selectSlot(int slot) { this.selectedSlot = slot; }
    void clearSelection() { this.selectedSlot = -1; }
}

class VendingMachine; // forward declaration

class VendingMachineState {
public:
    virtual ~VendingMachineState() = default;
    virtual void insertCoin(VendingMachine& machine) = 0;
    virtual void selectProduct(VendingMachine& machine, int slot) = 0;
    virtual void dispense(VendingMachine& machine) = 0;

class VendingMachine {
    std::shared_ptr<VendingMachineState> state;
    int selectedSlot = -1;

public:
    VendingMachine() : state(std::make_shared<NoCoinState>()) {}

    void insertCoin() {
        auto current = state; // keep the dispatching state alive through the call
        current->insertCoin(*this);
    }
    void selectProduct(int slot) {
        auto current = state;
        current->selectProduct(*this, slot);
    }
    void dispense() {
        auto current = state;
        current->dispense(*this);
    }

    void transitionTo(std::shared_ptr<VendingMachineState> next) {
        if (!next) throw std::invalid_argument("next state");
        state = std::move(next);
    }
    int selectedSlotId() const {
        if (selectedSlot < 0) throw std::logic_error("no selected slot");
        return selectedSlot;
    }
    void selectSlot(int slot) {
        if (slot < 0) throw std::invalid_argument("slot");
        selectedSlot = slot;
    }
    void clearSelection() { selectedSlot = -1; }
};

// Implementations that need VendingMachine to be complete
void NoCoinState::insertCoin(VendingMachine& machine) {
    std::cout << "Coin accepted\n";
    machine.transitionTo(std::make_shared<HasCoinState>());
}

void HasCoinState::selectProduct(VendingMachine& machine, int slot) {
    std::cout << "Product selected: slot " << slot << "\n";
    machine.selectSlot(slot);
    machine.transitionTo(std::make_shared<DispensingState>());
}

void DispensingState::dispense(VendingMachine& machine) {
    std::cout << "Dispensing product from slot " << machine.selectedSlotId() << "\n";
    machine.clearSelection();
    machine.transitionTo(std::make_shared<NoCoinState>());
}
The local shared_ptr in each dispatcher prevents replacing the context's pointer from destroying the currently executing C++ state object mid-call. A production design could avoid repeated allocation with stateless shared instances or have handlers return a next-state value that the context applies after dispatch.

class VendingMachineState(ABC):
    @abstractmethod
    def insert_coin(self, machine: "VendingMachine") -> None:
        pass

    @abstractmethod
    def select_product(self, machine: "VendingMachine", slot: int) -> None:
        pass

    @abstractmethod
    def dispense(self, machine: "VendingMachine") -> None:
        pass

        print("Coin accepted")
        machine._transition_to(HasCoinState())

    def select_product(self, machine: "VendingMachine", slot: int) -> None:
        print("Insert coin first")

    def dispense(self, machine: "VendingMachine") -> None:
        print("Insert coin first")

class HasCoinState(VendingMachineState):
    def insert_coin(self, machine: "VendingMachine") -> None:
        print("Coin already inserted")

            raise ValueError("slot must be non-negative")
        print(f"Product selected: slot {slot}")

    def dispense(self, machine: "VendingMachine") -> None:

        print("Please wait, dispensing in progress")

    def select_product(self, machine: "VendingMachine", slot: int) -> None:
        print("Already dispensing")

    def dispense(self, machine: "VendingMachine") -> None:
        print(f"Dispensing product from slot {machine._selected_slot_id()}")
        machine._clear_selection()

class VendingMachine:

        self._state.insert_coin(self)

        self._state.select_product(self, slot)

State objects localize the new state's cases, but they do not make existing transitions or composition magically immutable.

When Not to Use State Objects
Not every finite-state machine needs the State object pattern. The pattern adds types, references between state behavior and context, and an interface that represents the event surface.

Connect Four win checking does NOT need State pattern. Checking whether four tokens are connected in a row is fixed logic. It does not depend on what state the game is in. A simple method that scans rows, columns, and diagonals is the right approach. The game has states (Player 1's turn, Player 2's turn, Game Over), but the win-checking logic is the same regardless of whose turn it is.

Use an explicit state-machine model when: behavior or validity changes by lifecycle state. The vending machine's insertCoin() has different outcomes in NO_COIN, HAS_COIN, and DISPENSING. Then choose table/switch versus state objects based on the size and dependencies of each case.

Keep an enum/table/switch when: the transition matrix is small and cohesive, or behavior is largely state-independent. A two-state machine can still justify state objects if each state owns complex behavior; state count alone is not the criterion.

Strategy vs State: The Key Difference
Object-oriented versions of both patterns can use an interface with multiple implementations, but their semantics differ:

Strategy	State
What it represents	A selectable way to perform one role	A lifecycle phase with allowed events/transitions
Who changes it	Usually caller/composition policy	The context's lifecycle rules; a state object or transition table may compute the next state
Purpose	Select an interchangeable algorithm/policy	Model state-dependent validity, effects, and transitions
Lifetime	Can be fixed or selected per call	Changes when a valid domain event causes a transition
With Strategy, the ShoppingCart caller says "use PayPal for this checkout." The PayPal strategy has no idea CreditCard or Crypto strategies exist.

In this implementation, NoCoinState names HasCoinState. Another valid implementation can return a HAS_COIN value and let the context or transition table apply it, avoiding sibling-state references.

Interview tip: Ask what the variants mean. Strategies are alternative implementations of a role; states encode lifecycle-dependent validity and transition rules. “Who switches?” is a helpful clue, not a complete definition.

Quick Recap
Concept	What it means	Why it matters
Finite-state model	States, events, guards, effects, and next states are explicit	Makes invalid/missing transitions reviewable
State object pattern	Optional implementation where the context delegates state-specific behavior	Localizes substantial behavior by lifecycle phase
Transition ownership	State object, context, or table computes the next state	Choose deliberately; states need not reference siblings
When to use	Behavior or event validity changes by lifecycle state	Keeps the transition contract explicit
When to skip state objects	A small exhaustive enum/table is clearer, or logic is state-independent	Avoids unnecessary class navigation while retaining an explicit machine
