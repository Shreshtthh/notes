# Lesson 6

## Modeling Temporal Resources — Intervals vs Slots
**TL;DR:** When a resource is reserved for a period of time — a hotel room, a meeting room, a rental car — store the booking as a single interval row with start and end, not as one row per discrete slot. Slot tables are a denormalized cache of the interval, and they pay the cost (`O(duration)` storage and writes, bounded windows, timezone pain) without earning anything unless you're also attaching per-slot state like pricing.

### The Question That Trips Everyone Up
You're designing booking.com, Airbnb, a meeting room scheduler, or any system where somebody reserves a resource for a range of time. The question always comes in one of two shapes:

1. "Would you store start_date and end_date on each booking, or pre-populate a (room, date) table for the next 3 months with a nullable booking_id?"
2. "A room is free. How do you represent that?"

Both questions are asking the same thing: what is the entity? Is a booking the source of truth and availability a query over it — or is each day a slot that a booking happens to occupy?

The course's Derive vs Track State lesson already told you the answer in the discrete case (movie seats, showtimes): reservations are the source of truth, availability is derived. This lesson generalizes that principle to continuous-time resources — and shows you the one case where the slot-table pattern actually wins, so you know when not to apply the default.

### Two Schemas, One Decision

**Option A — Interval per booking (the default)**
```text
rooms     (room_id, hotel_id, room_type, ...)
bookings  (booking_id, room_id, guest_id,
           check_in  DATE,
           check_out DATE,
           status)
```
A booking is one row. A seven-night stay is one row. A cancellation updates status. A date change updates two columns.

Availability is a query: "is room X free from D1 to D2?"

```sql
SELECT 1
FROM   bookings
WHERE  room_id   = :room
  AND  status    = 'confirmed'
  AND  check_in  < :end       -- half-open interval [check_in, check_out)
  AND  check_out > :start;
```
If this returns nothing, the room is free for `[start, end)`. The classic interval-overlap test: two intervals `[a, b)` and `[c, d)` overlap iff `a < d` AND `c < b`.

> **Why half-open intervals?** `[check_in, check_out)` means a guest checking out on the 10th does not conflict with a guest checking in on the 10th. That's how real hotels work. Using closed intervals `[a, b]` forces you to write `check_in <= :end - 1 day` everywhere, which is fragile and timezone-hostile. Always model calendar intervals as half-open.

**Option B — One row per (room, day) slot**
```text
room_days (room_id, day DATE, booking_id NULL)
```
Seed the table with every room × every day for the next 90 days. A new booking sets `booking_id` on every day it covers. "Is room X free on day D?" is a single lookup.

This feels concrete and easy — so candidates reach for it first. That's the trap.

### The Default: Option A Wins
Seven reasons the interval form beats the slot form for hotel-shaped problems.

1. **The slot table is a materialized cache of the interval**
Everything the slot table knows can be derived from Option A with one query. You are storing the same truth (check_out − check_in) times. That's the exact "two copies of the same state" pattern the Derive vs Track State lesson warns about, just at the schema level instead of the class level.

2. **Storage grows O(rooms × days)**
100 hotels × 200 rooms × 365 days = 7.3M rows per year of mostly-empty metadata. Interval rows grow with actual bookings, not with the dimension of the calendar.

3. **Write amplification on every booking**
A 7-night stay touches 7 rows in Option B, 1 row in Option A. Cancellation touches 7, modification touches 7-to-14. Every operation pays the duration tax.

4. **The window is bounded**
"The next 3 months" means a cron job that extends the horizon. That job fails, or runs late, or hasn't been deployed yet in a new region, and suddenly a user trying to book 89 days out sees "no availability" when the room is clearly free. Option A has no window — it just stores intervals.

5. **Timezones and half-days are a nightmare at day granularity**
"Check-in 14:00, check-out 11:00" is natural in an interval model and incoherent in a slot model. DST changes don't affect intervals. Guest arrivals across midnight don't affect intervals. A slot table has to pick a convention and hold it forever.

6. **DB-enforced no-double-booking is a one-liner (Postgres)**
```sql
ALTER TABLE bookings
  ADD CONSTRAINT no_overlap
  EXCLUDE USING gist (
    room_id                                 WITH =,
    daterange(check_in, check_out, '[)')    WITH &&
  ) WHERE (status = 'confirmed');
```
The database itself rejects any insert that would create an overlapping booking on the same room. No application-level locks, no `SELECT ... FOR UPDATE`, no race condition. This is the killer argument for Option A — you get correctness for free from the storage layer. The slot-table approach can match it (unique `(room_id, day)` on a non-null `booking_id`) but only after you've paid the write amplification.

> **Interview tip:** Mentioning `EXCLUDE USING gist` in an interview is a cheap way to demonstrate that you know the database isn't just a dumb blob store. Most candidates either reach for table locks or hand-rolled "check then insert" logic that races. Naming the constraint that makes the race impossible is worth several rungs.

7. **The "easy" query isn't easier with proper indexing**
"Is room X free on day D" looks like a trivial lookup in Option B. But a composite B-tree index on `(room_id, check_in)` in Option A gives you the same `O(log N)` lookup for the same query, and answers "find me a free room for this 5-night range" — which Option B can only answer with a 5-row scan.

### The Anti-Default: When Slot Tables Actually Win
Option B is not always wrong. It's right in three specific cases — learn these so you can recognize the trap in the other direction.

**Case 1 — The slot row exists for its other columns**
Hotel yield management stores a price, a promo flag, an inventory bucket, and a channel override per `(room_type, date)`. Those columns are the real payload. "Is this slot booked" is a coincidental extra bit. In that case you already own the slot row for pricing reasons; availability tags on it are cheap.

```text
room_day_rates (room_type, day, base_price, promo_price,
                inventory_available, channel_overrides, ...)
```
If you're designing a revenue management system, Option B. If you're designing the booking engine that reads it, Option A plus a join to this table. The two coexist.

**Case 2 — The resource is fungible, not specific**
Airline seat inventory by fare class: you're not tracking which seat 23A is taken, you're decrementing a counter for "economy Y class on SFO-JFK on March 5." The entity is the counter, not the seat. That's a `(flight, date, class, seats_left)` table, which is literally Option B with an integer instead of a nullable id.

Same argument for: hotel room type inventory (where the specific room gets assigned at check-in), concert general admission, warehouse stock.

The key test: does the user care which specific asset they get, or just that they get one? Specific → Option A. Fungible → Option B.

**Case 3 — The slot IS the unit of sale**
Cinema seats are not interval reservations — they're "seat A5 for this specific showtime." There is no start and end, just showtime × seat. The course's Movie Ticket Booking mock models this correctly: each `Showtime` owns a `Set<String>` of reserved seat strings. That is Option B done right, because the entity genuinely is a slot.

Same argument for: 30-minute Calendly slots, fixed gym class times, doctor appointment slots on a grid. If the business pre-defines discrete slots and sells them individually, your schema should match.

### The Decision Tree
Ask three questions, in order, before picking a schema.

1. **Is the unit of reservation a continuous range, or a pre-defined slot on a fixed grid?**
   - Continuous range → keep going.
   - Discrete slot → Option B. Stop here.
2. **Do you also need per-day state beyond availability — pricing, inventory, promo flags?**
   - Yes → you'll have a slot table anyway for that state. Use it for availability too. Option B.
   - No → keep going.
3. **Is the resource specific (room #204, court #3) or fungible (an economy seat, a small car)?**
   - Specific → Option A. Interval row, overlap query, EXCLUDE USING gist.
   - Fungible → counter per slot. Option B, but the column is an integer not a nullable id.

Default to Option A. Reach for Option B only when questions 2 or 3 force it, and be prepared to justify the choice.

### A Worked Example in Java
Here's the minimum viable booking engine using Option A, with the overlap check in application code so you can see the interval arithmetic directly. In production the `EXCLUDE USING gist` constraint would enforce it at the DB layer; we're showing the logic so you can describe it in an interview even when the interviewer pushes back on "just add a DB constraint."

```java
class Booking {
    final String bookingId;
    final String roomId;
    final String guestId;
    final LocalDate checkIn;    // inclusive
    final LocalDate checkOut;   // exclusive — half-open interval
    BookingStatus status;

    boolean overlaps(LocalDate start, LocalDate end) {
        // Two half-open intervals [a, b) and [c, d) overlap iff a < d AND c < b.
        return checkIn.isBefore(end) && start.isBefore(checkOut);
    }
}

class BookingEngine {
    private final Map<String, List<Booking>> byRoom = new HashMap<>();

    boolean isAvailable(String roomId, LocalDate start, LocalDate end) {
        if (!start.isBefore(end)) {
            throw new IllegalArgumentException("Invalid range");
        }
        List<Booking> bookings = byRoom.getOrDefault(roomId, List.of());
        for (Booking b : bookings) {
            if (b.status == BookingStatus.CONFIRMED && b.overlaps(start, end)) {
                return false;
            }
        }
        return true;
    }

    Booking book(String roomId, String guestId, LocalDate start, LocalDate end) {
        if (!isAvailable(roomId, start, end)) {
            throw new IllegalStateException("Room not available for requested range");
        }
        Booking b = new Booking(UUID.randomUUID().toString(),
                                roomId, guestId, start, end, BookingStatus.CONFIRMED);
        byRoom.computeIfAbsent(roomId, k -> new ArrayList<>()).add(b);
        return b;
    }
}
```

Three things to notice:
1. `overlaps` is the only non-trivial line, and it's three operators. Interval arithmetic is embarrassingly simple once you commit to half-open semantics.
2. The per-room list is a naive O(bookings-per-room) scan. For a 1000-room hotel with a year of history this is fine. For Airbnb-scale (millions of listings) you'd index intervals with an interval tree or push the overlap check into Postgres — but the data model does not change. Only the lookup structure does.
3. Concurrency is untouched. In a real service you'd either take a pessimistic lock on the room while booking, use the `EXCLUDE` constraint and catch the conflict, or use optimistic concurrency with a retry. All three strategies work with Option A. None work cleanly with Option B's pre-populated rows.

### The Ownership Question
One more subtlety that catches people. When a booking exists, who owns the "this room is taken" fact — the room or the booking?

**Room-owns-availability (bad):** Room has a boolean `available` flag or a `List<DateRange>` unavailable field. Now `book()` has to mutate the room and create a booking, atomically, and you're back to the two-source-of-truth problem from the previous lesson.

**Booking-owns-the-interval (good):** Room has only intrinsic facts — id, type, capacity, amenities. Booking has the interval. "Is this room available" is a query over the set of bookings filtered by `room_id`. This is the same principle as the movie booking lesson: the reservation is the truth, the availability is derived.

If you catch yourself adding `available: boolean` or `nextFreeDate` or `isBooked` to the `Room` class in an interview, stop. Those are all derived facts. Store them on `Booking` and compute them on demand.

### What You Should Take Away
- A booking is an interval. The interval IS the entity. Every question — "is X free", "which X are free", "how many X-nights in March" — is a query, not a storage decision.
- Default to interval rows. Option B is only correct when the unit of sale is genuinely a discrete slot (cinema seats, Calendly), the row exists anyway for other per-slot state (yield management), or the resource is fungible so you're decrementing a counter not assigning an asset (airline inventory).
- Half-open intervals, always. `[check_in, check_out)`. Checkout day is not a conflict with the next guest's check-in day. Closed intervals force you to subtract a day everywhere and punish you for every timezone boundary you cross.
- `EXCLUDE USING gist` is your cheat code for "no double-booking" on Postgres. Name it in an interview even if you don't write the DDL — it signals that you know the DB has your back and you're not going to hand-roll a race condition.

This principle generalizes derive-vs-track-state from per-entity state to entire schemas. The two lessons are the same rule at different scales: don't store what you can compute cheaply, and when you store an interval, don't also store its per-day expansion.
