# Lesson 7

## Architecture as a Dependency DAG
**TL;DR:** A class diagram is a directed graph. Nodes are classes, edges are "depends on." If that graph has a cycle, the system is impossible to construct, impossible to test in isolation, and a sign that an abstraction is missing. Read your design as a graph, find the cycles, break them by introducing an interface or an event, and let the construction order fall out of a topological sort. Dependency Inversion is not a vague best practice -- it is "all edges must point toward stable, abstract nodes." This lesson gives you the graph-shaped lens that turns DI from intuition into a check.

### Why This Matters in Interviews
Most candidates can name SOLID's "D" -- Dependency Inversion -- and still ship a hierarchy where `OrderService` calls `EmailNotifier` directly, `EmailNotifier` reads back from `OrderService` to format the message, and the interviewer asks the killer question: "How do you unit-test this?" The candidate freezes because there is no way to construct an `OrderService` without an `EmailNotifier`, and no way to construct an `EmailNotifier` without an `OrderService`. The cycle exists in the design, but no one drew the graph that would have made it visible.

The graph view turns "is my design clean?" into a question with a yes/no answer. Are there cycles? If yes, the design is wrong, full stop. Do edges point from concrete to abstract? If yes, you can test, mock, swap, and instantiate freely. Interviewers who probe testability and extensibility are reading your code as a graph already; making that graph explicit is how you keep up with them.

### The Graph: Classes as Nodes, Dependencies as Edges
Read any class diagram as a directed graph `G=(V,E)`:

- `V` = the set of classes
- `E` = the set of dependency edges, where `A → B` means "class A holds a reference to or constructs class B"

A dependency exists if `A`'s code mentions `B` -- as a constructor argument, a field type, a return type, or a `new B()` call. The edge points from the user to the used.

Tell, don't ask: A field that's only there to call methods on is a dependency edge. A parameter that's only passed through to another method is a dependency edge. If you can't draw the edge without staring at the code for a minute, the dependency is hidden, which is its own design smell.

### The Pain: A Cycle Hidden in Plain Sight
Here's an order system the candidate types in five minutes:

```java
// BAD: implicit cycle between OrderService and EmailNotifier
class OrderService {
    private final EmailNotifier notifier;
    private final InventoryService inventory;

    public OrderService(EmailNotifier notifier, InventoryService inventory) {
        this.notifier = notifier;
        this.inventory = inventory;
    }

    public void placeOrder(Order order) {
        inventory.reserve(order);
        notifier.sendOrderConfirmation(order, this);
    }

    // EmailNotifier calls back into here to format the email
    public String formatOrderSummary(Order order) {
        return "Order " + order.getId() + ": " + order.getItems();
    }
}

class EmailNotifier {
    public void sendOrderConfirmation(Order order, OrderService source) {
        String body = source.formatOrderSummary(order);
        // ... send the email
    }
}
```

Draw the graph:
`OrderService → EmailNotifier → OrderService`

That's a cycle. Three things break instantly:

1. **Construction is impossible without trickery.** You can't build `OrderService` without `EmailNotifier`, but `EmailNotifier` needs the `OrderService` it will call back into. Any DI framework fails to wire this up; manual code requires a two-phase init or a setter, both of which are smells.
2. **Testing in isolation is impossible.** To unit-test `OrderService`, you need an `EmailNotifier`. To unit-test `EmailNotifier`, you need an `OrderService`. Any mock you write for one has to know about the other.
3. **The dependency direction is a lie.** The cycle says "these two classes are really one class pretending to be two." That's the actual design feedback the cycle is giving you.

The cycle exists because `EmailNotifier` reaches back into `OrderService` for formatting logic that doesn't belong to either of them. The fix isn't to wire the dependencies more cleverly -- it's to extract the missing abstraction.

### The Fix: Make the Graph Acyclic
A correct design is a DAG -- a directed acyclic graph. No cycles. Every cycle that appears during design tells you an abstraction is missing.

The fix here is to extract the order-summary formatting into its own concept and to invert the dependency from `EmailNotifier` so it depends on a small interface, not on `OrderService`:

```java
// GOOD: dependency edges all point one way
interface OrderSummary {
    String format(Order order);
}

class DefaultOrderSummary implements OrderSummary {
    public String format(Order order) {
        return "Order " + order.getId() + ": " + order.getItems();
    }
}

class EmailNotifier {
    private final OrderSummary summary;

    public EmailNotifier(OrderSummary summary) {
        this.summary = summary;
    }

    public void sendOrderConfirmation(Order order) {
        String body = summary.format(order);
        // ... send the email
    }
}

class OrderService {
    private final EmailNotifier notifier;
    private final InventoryService inventory;

    public OrderService(EmailNotifier notifier, InventoryService inventory) {
        this.notifier = notifier;
        this.inventory = inventory;
    }

    public void placeOrder(Order order) {
        inventory.reserve(order);
        notifier.sendOrderConfirmation(order);
    }
}
```

The new graph:
`OrderService → EmailNotifier → OrderSummary ← DefaultOrderSummary`

No cycles. `OrderSummary` is an abstract leaf -- the most stable, depend-on-able node. `OrderService`, `EmailNotifier`, and `DefaultOrderSummary` all point inward toward it but never at each other in a loop.

### Topological Sort = Construction Order
If your dependency graph is a DAG, it admits a topological sort: an ordering of nodes such that every edge points from earlier to later in the sequence. That ordering is exactly the construction order you write in `main`:

```java
// The topo sort: leaves first, roots last
public static void main(String[] args) {
    OrderSummary summary = new DefaultOrderSummary();           // depends on nothing
    InventoryService inventory = new InventoryService();        // depends on nothing
    EmailNotifier notifier = new EmailNotifier(summary);        // depends on summary
    OrderService orders = new OrderService(notifier, inventory); // depends on the above two

    orders.placeOrder(new Order(...));
}
```
A DI framework like Spring or Guice does this automatically: it reads the constructor signatures, builds the dependency graph, runs a topological sort, and instantiates objects in that order. If there's a cycle, the framework explodes at startup. That explosion is the framework telling you what your graph already knew -- the design is wrong.

> **Interview tip:** When an interviewer asks "how would you wire this up?" the answer is a topological-sort walk through your class diagram. You don't need to say "topological sort" -- but constructing leaves first and roots last, and being able to point at the order, signals that you understand the graph structure rather than memorizing DI as a buzzword.

### Dependency Inversion = Edges Point Toward Abstractions
The Dependency Inversion Principle from SOLID is a statement about edges, not classes. Restated as a graph rule:

*Every dependency edge must point from a less-abstract node to a more-abstract node.*

In the broken design, `EmailNotifier` (concrete) pointed at `OrderService` (concrete) -- a concrete-to-concrete edge. In the fixed design, `EmailNotifier` (concrete) points at `OrderSummary` (interface) -- a concrete-to-abstract edge. Same number of nodes, same number of edges, but every edge now obeys the rule.

The check is mechanical:
For every edge `A → B` in your class diagram, ask: is `B` at least as abstract as `A`?
- If yes, edge passes.
- If no, introduce an interface that captures only what `A` needs, point `A` at the interface, and let `B` implement it.

This is what "depend on abstractions, not concretions" means as a graph operation. You are not adding interfaces for the sake of it; you are reorienting edges so the graph has the right shape.

### Cycle-Breaking Toolkit
When the graph has a cycle, four moves typically break it:

| Move | When to use it | Example |
|---|---|---|
| Extract an interface | Two classes call each other for a single role | `OrderSummary` example above |
| Invert an edge with a callback | Class `A` needs to react to something `B` does | `B` takes a `Consumer<Event>` instead of calling `A` |
| Introduce an event bus / domain event | Many-to-many notifications between modules | `OrderPlaced` event published by `OrderService`, consumed by `EmailNotifier`, `Analytics`, etc. |
| Merge into one class | The two classes really are one concept | Cycle was telling you the split was wrong from the start |

The last one is underused. Some cycles aren't bugs in the dependency direction -- they're bugs in the class boundary. If `OrderService` and `OrderRepository` mutually call each other for every operation, they probably want to be one `OrderAggregate` class.

### Red Flags of Skipping the Graph View

| Red flag | What the graph view would have caught |
|---|---|
| Forward declarations / `TYPE_CHECKING` imports | A cycle the type system is forcing you to lie about |
| Setter injection where constructor injection should suffice | A cycle being broken by deferred wiring |
| `@PostConstruct` or two-phase init | Same -- you can't build the object in one step because the graph has a cycle |
| Singletons everywhere | Often used to escape the construction order problem; the graph view shows you the real fix is breaking cycles, not making everything global |
| "Utility" classes that everyone depends on | A node with very high in-degree and zero out-degree is fine for true utilities, but most utility classes are dumping grounds that hide a missing abstraction |

### Quick Recap

| Concept | What it means | Why it matters |
|---|---|---|
| Graph `G=(V,E)` | Classes are nodes, dependencies are directed edges | The design's structure becomes inspectable as a graph |
| DAG requirement | No cycles allowed | Cycles = impossible to construct, test, or reason about |
| Topological sort | Leaves first, roots last | The construction order falls out automatically |
| DIP as a graph rule | Every edge points toward a more-abstract node | Mechanical check, not vague best practice |
| Cycle-breaking moves | Interface, callback, event, or merge | Each cycle has a diagnostic value -- it tells you what abstraction is missing |
