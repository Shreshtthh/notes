# Lesson 3

## Fine-Grained Locking and Deadlock Prevention

**TL;DR:** Fine-grained locking partitions both locks and the state they protect, allowing unrelated operations to overlap. When an operation needs several locks, every code path must use one global order. Ordering removes circular waits among those locks; it does not prevent every deadlock caused by callbacks, blocking I/O, or other lock families.

---

## Fine-Grained vs Coarse-Grained Locking

### When Coarse-Grained Becomes a Bottleneck

In a ticket booking system, coarse-grained locking means a single lock on the entire venue. When Alice books seat 7A, Bob cannot book seat 12B until Alice is done — even though the two seats are completely independent.

For human-triggered booking, this is fine. But consider a flash sale: 10,000 automated agents all trying to book seats the instant they go on sale. Every booking request waits in line behind one lock. The lock becomes the bottleneck.

The fix: give each seat its own lock and assignment field. Merely adding seat locks around concurrent writes to one ordinary `HashMap` would leave the shared container unsafe.

```java
class TicketBookingSystem {
    private static final class Seat {
        final Lock lock = new ReentrantLock();
        String assignedUser; // accessed only while lock is held
    }

    private final Map<String, Seat> seats;

    public TicketBookingSystem(List<String> seatIds) {
        Map<String, Seat> built = new HashMap<>();
        for (String id : seatIds) {
            if (id == null || id.isBlank()) throw new IllegalArgumentException("blank seat id");
            if (built.putIfAbsent(id, new Seat()) != null)
                throw new IllegalArgumentException("duplicate seat id: " + id);
        }
        seats = Map.copyOf(built);
    }

    public boolean bookSeat(String seatId, String userId) {
        Objects.requireNonNull(userId, "userId");
        Seat seat = requireSeat(seatId);
        seat.lock.lock();
        try {
            if (seat.assignedUser != null) return false;
            seat.assignedUser = userId;
            return true;
        } finally {
            seat.lock.unlock();
        }
    }

    private Seat requireSeat(String seatId) {
        Seat seat = seats.get(seatId);
        if (seat == null) throw new IllegalArgumentException("unknown seat: " + seatId);
        return seat;
    }
}
```

Now Alice locks only seat 7A, and Bob locks only seat 12B. They proceed in parallel. No contention.

```cpp
class TicketBookingSystem {
    struct Seat {
        std::mutex mutex;
        std::optional<std::string> assignedUser;
    };

    std::unordered_map<std::string, std::unique_ptr<Seat>> seats;

public:
    TicketBookingSystem(const std::vector<std::string>& seatIds) {
        for (const auto& id : seatIds) {
            if (id.empty()) throw std::invalid_argument("blank seat id");
            if (!seats.emplace(id, std::make_unique<Seat>()).second)
                throw std::invalid_argument("duplicate seat id");
        }
    }

    bool bookSeat(const std::string& seatId, const std::string& userId) {
        if (userId.empty()) throw std::invalid_argument("blank user id");
        Seat& seat = *seats.at(seatId);
        std::lock_guard<std::mutex> lock(seat.mutex);
        if (seat.assignedUser) return false;
        seat.assignedUser = userId;
        return true;
    }
};
```

## Deadlock: The Price of Fine-Grained Locking

### Deadlock — Circular Wait

Now add a feature that moves a booking between seats. Alice tries to move from 7A to 12B while Bob tries to move from 12B to 7A. Both seats must be locked so the ownership check and move form one atomic operation.

**Bad Pattern**
```java
// BROKEN: deadlock-prone when opposite moves acquire in argument order
public boolean moveSeat(String seatA, String seatB, String userId) {
    Seat from = requireSeat(seatA);
    Seat to = requireSeat(seatB);
    from.lock.lock();
    to.lock.lock();
    try {
        return false; // the deadlock schedule occurs before movement checks
    } finally {
        to.lock.unlock();
        from.lock.unlock();
    }
}
```

```text
Alice: moveSeat("7A", "12B", "alice")     Bob: moveSeat("12B", "7A", "bob")
──────────────────────────────────────     ────────────────────────────────────
lock("7A") ✓                               lock("12B") ✓
lock("12B") ... waiting (Bob has it)       lock("7A") ... waiting (Alice has it)
```

Alice holds 7A and waits for 12B. Bob holds 12B and waits for 7A. Neither can proceed. This is a deadlock -- a circular wait where two or more threads are permanently blocked.

### The Fix: Consistent Lock Ordering

If every thread always acquires locks in the same order, circular wait is impossible. The simplest approach: sort the lock keys alphabetically (or numerically) and always lock in that order.

```java
public boolean moveSeat(String seatA, String seatB, String userId) {
    if (seatA.equals(seatB)) throw new IllegalArgumentException("distinct seats required");

    // Always lock in alphabetical order
    String first = seatA.compareTo(seatB) < 0 ? seatA : seatB;
    String second = seatA.compareTo(seatB) < 0 ? seatB : seatA;
    Seat firstSeat = requireSeat(first);
    Seat secondSeat = requireSeat(second);

    firstSeat.lock.lock();
    secondSeat.lock.lock();
    try {
        Seat from = requireSeat(seatA);
        Seat to = requireSeat(seatB);
        if (!userId.equals(from.assignedUser)) return false;
        if (to.assignedUser != null) return false;

        from.assignedUser = null;
        to.assignedUser = userId;
        return true;
    } finally {
        secondSeat.lock.unlock();
        firstSeat.lock.unlock();
    }
}
```

Now both Alice and Bob try to lock "12B" first (it comes before "7A" alphabetically). One of them wins, the other waits. No circular wait.

```cpp
class OrderedSeatMover {
    struct Seat {
        std::mutex mutex;
        std::optional<std::string> assignedUser;
    };
    std::unordered_map<std::string, std::unique_ptr<Seat>> seats;

public:
    explicit OrderedSeatMover(const std::vector<std::string>& seatIds) {
        for (const auto& id : seatIds) {
            if (!seats.emplace(id, std::make_unique<Seat>()).second)
                throw std::invalid_argument("duplicate seat id");
        }
    }

    bool moveSeat(const std::string& seatA, const std::string& seatB,
                  const std::string& userId) {
        if (seatA == seatB) throw std::invalid_argument("distinct seats required");
        const std::string& first = (seatA < seatB) ? seatA : seatB;
        const std::string& second = (seatA < seatB) ? seatB : seatA;
        Seat& firstSeat = *seats.at(first);
        Seat& secondSeat = *seats.at(second);

        std::lock_guard<std::mutex> lock1(firstSeat.mutex);
        std::lock_guard<std::mutex> lock2(secondSeat.mutex);

        Seat& from = *seats.at(seatA);
        Seat& to = *seats.at(seatB);
        if (from.assignedUser != userId || to.assignedUser) return false;
        to.assignedUser = userId;
        from.assignedUser.reset();
        return true;
    }
};
```

### Inventory Management: Another Lock-Ordering Example

An inventory system manages multiple warehouses. Transferring stock between warehouses requires locking both:

```java
class InventorySystem {
    private static final class Warehouse {
        private final Map<String, Integer> stock = new HashMap<>();

        Warehouse(Map<String, Integer> initialStock) {
            initialStock.forEach((item, qty) -> {
                if (qty < 0) throw new IllegalArgumentException("negative stock");
                stock.put(item, qty);
            });
        }

        int getStock(String item) { return stock.getOrDefault(item, 0); }
        void setStock(String item, int qty) { stock.put(item, qty); }
    }

    private final Map<String, Warehouse> warehouses;
    private final Map<String, Lock> warehouseLocks;

    InventorySystem(Map<String, Map<String, Integer>> initialStock) {
        Map<String, Warehouse> builtWarehouses = new HashMap<>();
        Map<String, Lock> builtLocks = new HashMap<>();
        initialStock.forEach((id, stock) -> {
            builtWarehouses.put(id, new Warehouse(Map.copyOf(stock)));
            builtLocks.put(id, new ReentrantLock());
        });
        warehouses = Map.copyOf(builtWarehouses);
        warehouseLocks = Map.copyOf(builtLocks);
    }

    public boolean transfer(String fromId, String toId, String item, int qty) {
        if (fromId.equals(toId)) throw new IllegalArgumentException("distinct warehouses required");
        if (qty <= 0) throw new IllegalArgumentException("quantity must be positive");
        if (!warehouses.containsKey(fromId) || !warehouses.containsKey(toId))
            throw new IllegalArgumentException("unknown warehouse");

        // Consistent ordering: alphabetical by warehouse ID
        String first = fromId.compareTo(toId) < 0 ? fromId : toId;
        String second = fromId.compareTo(toId) < 0 ? toId : fromId;

        warehouseLocks.get(first).lock();
        warehouseLocks.get(second).lock();
        try {
            Warehouse from = warehouses.get(fromId);
            Warehouse to = warehouses.get(toId);

            int fromStock = from.getStock(item);
            if (fromStock < qty) return false;
            int newFromStock = Math.subtractExact(fromStock, qty);
            int newToStock = Math.addExact(to.getStock(item), qty);

            // Compute every fallible arithmetic result before mutating either warehouse.
            from.setStock(item, newFromStock);
            to.setStock(item, newToStock);
            return true;
        } finally {
            warehouseLocks.get(second).unlock();
            warehouseLocks.get(first).unlock();
        }
    }
}
```

Two simultaneous transfers—warehouse A to B and warehouse B to A—both lock A first because A < B, so these warehouse locks cannot form a cycle. The immutable registry matters too: adding/removing warehouses concurrently would require its own synchronization and a lock-lifecycle policy.

### Collect Under Lock, Fire Outside

When you hold a lock, keep work bounded. In particular, avoid network calls, blocking I/O, and callbacks into code whose locking behavior you do not control. They lengthen the critical section and can introduce a lock cycle or re-entrant mutation.

**Bad:**
```java
public boolean bookSeat(String seatId, String userId) {
    lock.lock();
    try {
        if (seatAssignments.containsKey(seatId)) return false;
        seatAssignments.put(seatId, userId);
        notificationService.send(userId, "Seat " + seatId + " booked!");  // I/O under lock!
        return true;
    } finally {
        lock.unlock();
    }
}
```

Every waiter inherits the notification call's delay. A callback that takes other locks can also create a cycle. Re-acquiring a Java `ReentrantLock` on the same thread is permitted, but that does not make arbitrary callback paths safe; a non-reentrant lock, cross-thread callback, or different lock order can still deadlock.

**Good -- collect under lock, fire outside:**
```java
public boolean bookSeat(String seatId, String userId) {
    String notification = null;

    lock.lock();
    try {
        if (seatAssignments.containsKey(seatId)) return false;
        seatAssignments.put(seatId, userId);
        notification = "Seat " + seatId + " booked!";  // collect the data
    } finally {
        lock.unlock();
    }

    // Fire outside the lock
    if (notification != null) {
        notificationService.send(userId, notification);
    }
    return true;
}
```

The pattern: collect immutable data for the side effect while holding the lock, then fire after releasing it. This reduces lock hold time and removes the callback from that critical section.

It does not make the state change and notification atomic. In these snippets, booking succeeds before send; if sending fails, the caller can receive an exception even though the seat remains booked. For “never lose the notification” semantics, persist the booking and an outbox record atomically, then let an idempotent worker deliver and retry it. A local callback pattern and a transactional outbox solve different problems.

> [!TIP]
> **Interview tip:** If the interviewer asks "what if we need to send a notification when a seat is booked?", mention this pattern by name: "I would collect the notification details under the lock, then send the notification after releasing it." It shows you understand both performance and deadlock prevention.

## Quick Recap

- **Fine-grained locking** uses a separate lock per entity (per seat, per warehouse, per account). Unrelated operations proceed in parallel.
- **Deadlock** occurs when two threads each hold a lock the other needs, creating a circular wait.
- **Consistent lock ordering** prevents circular wait among the locks that obey that global order; it is not a blanket proof that the whole program cannot deadlock.
- **Collect under lock, fire outside** removes external code from the critical section; durable side effects additionally need an outbox/retry contract.
- Only use fine-grained locking when you can show that coarse-grained is a bottleneck. It adds complexity (deadlock risk, more code) for parallelism you may not need.
