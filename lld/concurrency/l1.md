# Cheat Sheet: Lesson 1

### Correctness — What Breaks Under Threads
**TL;DR:** Two common shared-state race patterns are check-then-act (another thread invalidates a checked condition before the action) and read-modify-write (two threads compute from the same old value and one update is lost). They are not the whole concurrency field: visibility, ordering, deadlock, starvation, and unsafe publication matter too.

### The Parking Lot Bug
You already built a Parking Lot system. Here is the `enter()` method, simplified:

#### Check-Then-Act Race Condition

```java
enum VehicleType { CAR }
record Vehicle(VehicleType type) {
    VehicleType getType() { return type; }
}

class ParkingLot {
    private final Map<String, Vehicle> spots = new HashMap<>();

    public String enter(Vehicle vehicle) {
        // Step 1: Find an available spot
        String spot = findAvailableSpot(vehicle.getType());
        if (spot == null) {
            throw new ParkingFullException("No spots available");
        }

        // Step 2: Assign the vehicle to the spot
        spots.put(spot, vehicle);
        return spot;
    }

    private String findAvailableSpot(VehicleType type) {
        for (String id : getAllSpots(type)) {
            if (!spots.containsKey(id)) {
                return id;
            }
        }
        return null;
    }

    private List<String> getAllSpots(VehicleType type) {
        return List.of("A1"); // deliberately tiny race demonstration
    }

    static class ParkingFullException extends RuntimeException {
        ParkingFullException(String message) { super(message); }
    }
}
```

This works perfectly in a single-threaded world. Now imagine two cars arrive at the same time:

```text
Thread A (Honda)                    Thread B (Toyota)
─────────────────                   ─────────────────
findAvailableSpot() → "A1"
                                    findAvailableSpot() → "A1"
spots.put("A1", honda)
                                    spots.put("A1", toyota)  // overwrites Honda!
```

Honda's driver walks to spot A1 and finds a Toyota there. This is a check-then-act race condition: the check (is A1 available?) and the act (assign A1) are not atomic. Another thread slips in between and invalidates the check.

### The Pattern: Check-Then-Act
Any time your code says `"if this condition is true, do this thing,"` ask: could another thread change this condition between the check and the action?

Common examples from systems you already built:

| System | The Check | The Act | What Breaks |
|---|---|---|---|
| Parking Lot | Is spot available? | Assign vehicle | Two cars get same spot |
| Ticket Booking | Is seat available? | Book seat | Double booking |
| LRU Cache | Is there room for another entry? | Insert entry | Cache exceeds capacity |
| Rate Limiter | Is count < limit? | Allow request | Limit exceeded |

The structure is always the same:

**Bad Pattern**
```java
// BROKEN: check-then-act
if (condition()) {    // Thread B can change the world here
    act();            // the action may now be invalid
}
```

Here is a concrete example -- a ticket booking counter:

**Bad Pattern**
```java
// BROKEN: Check-then-act race condition
class TicketCounter {
    private int availableTickets = 100;

    public boolean bookTicket() {
        if (availableTickets > 0) {       // Thread A checks: 1 ticket left
            // Thread B also checks here: still sees 1 ticket left!
            availableTickets--;            // Both calls can report success for one ticket
            return true;
        }
        return false;
    }
}
```

The fix is making the check and the act atomic with a lock:

**Refactored**
```java
// FIXED: Lock makes check-and-act atomic
class TicketCounter {
    private int availableTickets = 100;
    private final Object lock = new Object();

    public boolean bookTicket() {
        synchronized (lock) {
            if (availableTickets > 0) {
                availableTickets--;
                return true;
            }
            return false;
        }
    }
}
```

With the lock, Thread B blocks on `synchronized` until Thread A finishes the entire check-and-decrement sequence. By the time Thread B enters, it sees `availableTickets == 0` and correctly returns `false`. This relies on every access to `availableTickets` following the same locking protocol.

## Read-Modify-Write
### Lost Update — Read-Modify-Write Race

The second pattern is simpler but equally dangerous. Consider a simplified quota counter (a real per-second limiter would also need a well-defined window and clock):

```java
class RateLimiter {
    private int count = 0;
    private int limit = 100;

    public boolean allowRequest() {
        if (count < limit) {
            count++;     // read count, add 1, write count
            return true;
        }
        return false;
    }
}
```

The `count++` looks like one operation, but it is three: read the current value, add one, write the new value.

```text
Thread A                            Thread B
────────                            ────────
Read count → 5
                                    Read count → 5
Compute 5 + 1 = 6
                                    Compute 5 + 1 = 6
Write count = 6
                                    Write count = 6  // should be 7!
```

Two requests came in, but the counter only went up by one. This is a lost update, so the implementation can admit more successful calls than its recorded count.

```cpp
class RateLimiter {
    int count = 0;
    int limit = 100;

public:
    bool allowRequest() {
        if (count < limit) {
            count++;     // not atomic -- same race condition
            return true;
        }
        return false;
    }
};
```
*Note on Python: Do not use the GIL as the correctness contract for compound shared-state operations. CPython can switch threads between bytecode instructions and releases the GIL around blocking work; Python 3.13 also introduced an optional free-threaded build. Python's own documentation recommends explicit synchronization rather than depending on implementation-level internal locks. See CPython's thread/GIL notes and free-threading guidance.*

### The Pattern: Read-Modify-Write
Any time you read a value, compute something from it, and write it back, another thread can do the same computation on the stale value.

**Bad Pattern**
```java
// BROKEN: read-modify-write
int current = counter.get();     // read
int next = current + 1;          // modify
counter.set(next);               // write -- another thread may have already incremented
```

## More Check-Then-Act Examples

### Connection Pool
```java
interface Connection {}

class ConnectionPool {
    private List<Connection> available = new ArrayList<>();

    // BROKEN: check-then-act
    public Connection acquire() {
        if (!available.isEmpty()) {        // Thread A: pool has 1 connection
            // Thread B also sees 1 connection here!
            return available.remove(0);    // Both try to remove -- one gets IndexOutOfBoundsException
        }
        throw new NoConnectionAvailableException();
    }

    static class NoConnectionAvailableException extends RuntimeException {}
}
```
Two threads can both pass the check against one available connection. In the illustrated interleaving, the first `remove(0)` succeeds and the second reaches an empty list. More generally, concurrent unsynchronized access to `ArrayList` is outside its contract, so the exact symptom is not something the design may rely on.

### LRU Cache Eviction
```java
class LRUCache<K, V> {
    private final Map<K, V> cache = new LinkedHashMap<>(16, 0.75f, true);
    private int maxSize = 100;

    // BROKEN: check-then-act
    public void put(K key, V value) {
        if (cache.size() >= maxSize) {   // Thread A: size is 100, needs eviction
            evictOldest();               // Thread A evicts, size is now 99
        }                                // Thread B: also saw size 100, also evicts -- size drops to 98!
        cache.put(key, value);           // Both insert -- size goes to 100 from 98
    }

    private void evictOldest() {
        Iterator<K> keys = cache.keySet().iterator();
        if (keys.hasNext()) {
            keys.next();
            keys.remove();
        }
    }
}
```
The check ("are we at capacity?") and the eviction/insertion sequence are not atomic. An interleaving can over-evict or exceed the capacity. There is a second problem too: `LinkedHashMap` itself does not support unsynchronized concurrent mutation, so this example is only a race sketch, not a complete catalogue of possible outcomes.

### Rate Limiter with Time Window
```java
class SlidingWindowRateLimiter {
    private List<Long> timestamps = new ArrayList<>();
    private int limit = 100;
    private long windowMs = 1000;

    // BROKEN: check-then-act
    public boolean allowRequest() {
        long now = System.currentTimeMillis();
        timestamps.removeIf(t -> t < now - windowMs);  // clean old entries
        if (timestamps.size() < limit) {                // check: under limit?
            timestamps.add(now);                         // act: record request
            return true;
        }
        return false;
    }
}
```
Two threads can call `allowRequest()` when the count is 99, both pass the capacity check, and both attempt to add. That violates the intended admission invariant. `ArrayList` also cannot be mutated concurrently without external synchronization, so even `"the list ends at 101"` is only one possible interleaving, not a guaranteed symptom.

## More Read-Modify-Write Examples

### Hit Counter
```java
class HitCounter {
    private Map<String, Integer> counts = new HashMap<>();

    // BROKEN: read-modify-write
    public void recordHit(String page) {
        int current = counts.getOrDefault(page, 0);  // read
        counts.put(page, current + 1);                // modify + write
    }
}
```
Thread A reads count for "/home" as 42. Thread B reads count for "/home" as 42. Both write 43. One hit is lost. The loss rate depends on workload and scheduling; there is no defensible fixed percentage without measurement.

### Bank Account
```java
class BankAccount {
    private long balanceMinor = 100_000;

    // BROKEN: read-modify-write
    public boolean withdraw(long amountMinor) {
        if (balanceMinor >= amountMinor) {             // also check-then-act!
            balanceMinor = balanceMinor - amountMinor; // read-modify-write
            return true;
        }
        return false;
    }
}
```
Balance is `$1000`. Thread A withdraws `$800`: reads `$1000`, computes `$200`. Thread B withdraws `$700`: reads `$1000`, computes `$300`. Thread A writes `$200`. Thread B writes `$300`. Both calls can report success even though their combined `$1500` withdrawal exceeded the starting balance. The final stored value also fails to reflect both results. This combines check-then-act and read-modify-write.

### Metrics Aggregator
```java
class MetricsAggregator {
    private double totalLatency = 0;
    private int requestCount = 0;

    // BROKEN: two read-modify-writes that should be atomic together
    public void record(double latency) {
        totalLatency += latency;   // read-modify-write #1
        requestCount++;            // read-modify-write #2
    }

    public double getAverageLatency() {
        return totalLatency / requestCount;  // reads two values that may be inconsistent
    }
}
```
Even if each field were individually atomic, the two updates are not atomic together. A thread calling `getAverageLatency()` might see the updated `totalLatency` but the old `requestCount`, producing a wildly incorrect average.

### Visual Timeline: The Lost Update
Here is exactly what happens in memory during a lost update on a counter starting at 5:

```text
Time    Thread A                    Thread B                    Memory (count)
────    ────────                    ────────                    ──────────────
T1      READ count → 5                                         5
T2                                  READ count → 5             5
T3      COMPUTE 5 + 1 = 6                                     5
T4                                  COMPUTE 5 + 1 = 6         5
T5      WRITE count = 6                                       6
T6                                  WRITE count = 6            6  ← should be 7!
```
Two increments happened. The counter went up by one. Thread A's write is completely invisible -- it was overwritten by Thread B, who computed from the same stale value.

With more threads and operations, the expected final value remains deterministic but the observed wrong value is not. A test may occasionally appear to pass, and changing the runtime, CPU, logging, or debugger can change the interleaving. That nondeterminism is why stress tests can expose a race but cannot prove unsynchronized code safe.

## Combining Both Patterns
Most real bugs combine check-then-act with read-modify-write. The LRU cache is a good example:

```java
class LRUCache<K, V> {
    private final Map<K, V> cache = new LinkedHashMap<>(16, 0.75f, true);
    private int maxSize;

    public void put(K key, V value) {
        if (cache.size() >= maxSize) {   // check: are we at capacity?
            evictOldest();                // act: evict
        }
        cache.put(key, value);           // read-modify-write on the map
    }

    private void evictOldest() {
        Iterator<K> keys = cache.keySet().iterator();
        if (keys.hasNext()) {
            keys.next();
            keys.remove();
        }
    }
}
```
Thread A checks size (99, under max of 100), Thread B checks size (99, under max of 100), both skip eviction, both insert. Cache is now at 101 -- the invariant is broken.

### The Lost Update Pattern Explained with Concrete Numbers
The "lost update" is the most common concurrency bug in production systems. Let us trace through it precisely with a bank account.

Setup: Account balance is `$1,000`. Thread A deposits `$200`. Thread B deposits `$300`. Expected final balance: `$1,500`.

```text
Time   Thread A (deposit $200)          Thread B (deposit $300)          balance in memory
────   ──────────────────────           ──────────────────────           ─────────────────
T1     read balance → $1,000                                            $1,000
T2                                      read balance → $1,000           $1,000
T3     compute $1,000 + $200 = $1,200                                   $1,000
T4                                      compute $1,000 + $300 = $1,300  $1,000
T5     write balance = $1,200                                           $1,200
T6                                      write balance = $1,300          $1,300  ← WRONG
```
Final balance: `$1,300`. Thread A's `$200` deposit vanished completely. The same logical anomaly appears in databases as a lost update. Preventing it may require an in-process lock, an atomic operation, optimistic version checking, or an appropriate transaction; `"use transaction isolation"` is not one universal setting independent of the workload and storage engine.

Why the name "lost update": Thread A's update (`$1,200`) was written and then immediately overwritten by Thread B's update (`$1,300`). Thread B computed its result from the stale pre-Thread-A value. Thread A's work is lost.

The fix with a lock:

```java
class BankAccount {
    private long balanceMinor;
    private final Object lock = new Object();

    public void deposit(long amountMinor) {
        synchronized (lock) {
            balanceMinor = Math.addExact(balanceMinor, amountMinor);
        }
    }
}
```
With the lock, Thread B cannot read the balance until Thread A's entire deposit completes. Thread B reads `$1,200` (Thread A's result), adds `$300`, and writes `$1,500`. Both deposits are reflected.

## Combined Bug: The Metrics Aggregator
Here is a particularly nasty example that combines both patterns. A metrics service tracks request count and total latency to compute average latency:

**Bad Pattern**
```java
// BROKEN: two read-modify-writes that should be atomic together
class MetricsAggregator {
    private long totalLatencyMs = 0;
    private long requestCount = 0;

    public void record(long latencyMs) {
        totalLatencyMs += latencyMs;   // read-modify-write #1
        requestCount++;                 // read-modify-write #2
    }

    public double getAverageLatency() {
        if (requestCount == 0) return 0;
        return (double) totalLatencyMs / requestCount;
    }
}
```
* **Bug 1 (lost updates):** Two threads call `record()` simultaneously. Both can read `requestCount` as 100 and both write 101, losing one increment. The size of the error depends on the actual interleavings.
* **Bug 2 (inconsistent snapshot):** `getAverageLatency()` reads `totalLatencyMs` (which includes Thread A's latest recording) and `requestCount` (which does not yet reflect Thread A's increment). The average is computed from mismatched numerator and denominator.

The fix: wrap everything in one lock.

```java
class MetricsAggregator {
    private long totalLatencyMs = 0;
    private long requestCount = 0;
    private final Object lock = new Object();

    public void record(long latencyMs) {
        synchronized (lock) {
            totalLatencyMs += latencyMs;
            requestCount++;
        }
    }

    public double getAverageLatency() {
        synchronized (lock) {
            if (requestCount == 0) return 0;
            return (double) totalLatencyMs / requestCount;
        }
    }
}
```

## How to Spot These in an Interview
When you finish designing a system, ask yourself these two questions:

1. **"Do I check a condition and then act on it?"** -- If yes, another thread could change the condition between check and act.
2. **"Do I read a value, compute from it, and write it back?"** -- If yes, another thread could read the same stale value.

If the answer is yes and shared state can change concurrently without a synchronization contract, you likely have a race. A lock is one fix; a single atomic operation, confinement, immutability, or a transactional store may fit better.

> **Interview tip:** In an LLD interview, proactively mentioning `"this method has a check-then-act race -- we need synchronization"` is a strong signal. You don't need to be asked about concurrency to bring it up.

### Quick Recap
* **Check-then-act:** a condition is checked, then an action is taken based on it. Another thread can invalidate the condition between the two steps.
* **Read-modify-write:** a value is read, a new value is computed, and the result is written back. Another thread can read the same stale value and overwrite your update.
* These are two recurring race shapes, not an exhaustive taxonomy of concurrency failures.
* The fix is to give the whole invariant one synchronization protocol—for example a lock, an atomic compound operation, confinement, or a transaction.
