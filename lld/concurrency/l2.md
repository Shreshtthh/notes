Coarse-Grained Locking
TL;DR: A single lock around one object's invariant is the easiest correct baseline. Keep the protected section small, make every participating access follow the same protocol, and measure contention before splitting the lock. Request rate alone cannot tell you whether the lock is a bottleneck.

Fixing the Parking Lot
In the previous lesson, two threads both found spot A1 available and both assigned their vehicle to it. The fix: make sure only one thread can run the check-and-assign sequence at a time.

Java
Copy
enum VehicleType { CAR }
record Vehicle(VehicleType type) {
    VehicleType getType() { return type; }
}

class ParkingLot {
    private final Map<String, Vehicle> spots = new HashMap<>();
    private final List<String> allSpots = List.of("A1", "A2");

    public synchronized String enter(Vehicle vehicle) {
        String spot = findAvailableSpot(vehicle.getType());
        if (spot == null) {
            throw new ParkingFullException("No spots available");
        }
        spots.put(spot, vehicle);
        return spot;
    }

    public synchronized void exit(String spotId) {
        spots.remove(spotId);
    }

    private String findAvailableSpot(VehicleType type) {
        for (String id : getAllSpots(type)) {
            if (!spots.containsKey(id)) {
                return id;
            }
        }
        return null;
    }

    private List<String> getAllSpots(VehicleType type) {
        return allSpots; // this small example has one compatible spot type
    }

    static class ParkingFullException extends RuntimeException {
        ParkingFullException(String message) { super(message); }
    }
}
An instance synchronized method acquires that instance's monitor before entering and releases it on normal or exceptional exit. While Thread A is inside enter(), another thread calling a method synchronized on the same object waits. The monitor also supplies the Java Memory Model visibility edge discussed in Lesson 9.

Code
Copy
Thread A (Honda)                    Thread B (Toyota)
─────────────────                   ─────────────────
acquire lock
findAvailableSpot() → "A1"
spots.put("A1", honda)
release lock
                                    acquire lock
                                    findAvailableSpot() → "A2"  (A1 is taken now)
                                    spots.put("A2", toyota)
                                    release lock
Thread B sees the world as Thread A left it. No more double-assignment.

Python
Copy
enum class VehicleType { Car };

struct Vehicle {
    VehicleType type;
    VehicleType getType() const { return type; }
};

class ParkingFullException : public std::runtime_error {
public:
    using std::runtime_error::runtime_error;
};

class ParkingLot {
    std::unordered_map<std::string, Vehicle> spots;
    std::mutex mtx;
    const std::vector<std::string> allSpots{"A1", "A2"};

public:
    std::string enter(const Vehicle& vehicle) {
        std::lock_guard<std::mutex> lock(mtx);
        std::string spot = findAvailableSpot(vehicle.getType());
        if (spot.empty()) {
            throw ParkingFullException("No spots available");
        }
        spots.insert_or_assign(spot, vehicle);
        return spot;
    }

    void exit(const std::string& spotId) {
        std::lock_guard<std::mutex> lock(mtx);
        spots.erase(spotId);
    }

private:
    std::string findAvailableSpot(VehicleType type) {
        for (const auto& id : getAllSpots(type)) {
            if (spots.find(id) == spots.end()) {
                return id;
            }
        }
        return "";
    }

    const std::vector<std::string>& getAllSpots(VehicleType) const {
        return allSpots;
    }
};
When One Lock Is Enough
One lock is attractive because its correctness boundary is easy to state: while the lock is held, no other thread following the protocol can observe or mutate a half-applied invariant. It may still be the wrong boundary if protected work performs I/O, blocks on another service, or combines unrelated resources.

A useful first estimate is:

Code
Copy
offered serialized work = arrival rate × average time holding this lock
This dimensionless value estimates how much single-lock capacity the workload asks for. It is not the probability a caller waits, a latency percentile, or a universal pass/fail threshold. Arrival bursts, service-time variance, the number of caller threads, scheduling, fairness, and work done while holding the lock all affect queueing. Lock acquisition also has no portable fixed nanosecond cost: uncontended and contended paths differ by runtime, JVM state, operating system, and hardware.

So the interview answer is conditional: begin with one lock when it gives the right in-process invariant, keep I/O and callbacks outside it, then use profiling and wait-time metrics to decide whether contention warrants a more complex design. A human clicking a button does not imply low contention if many humans or services share one hot object.

Common Mistake #1: Releasing the Lock Between Check and Update
This is the most common mistake people make:

Java
Bad Pattern
Copy
// BROKEN: releasing lock between check and update
public String enter(Vehicle vehicle) {
    String spot;
    synchronized (this) {
        spot = findAvailableSpot(vehicle.getType());
    }
    // Lock is released here! Another thread can grab the same spot.
    if (spot == null) {
        throw new ParkingFullException("No spots available");
    }
    synchronized (this) {
        spots.put(spot, vehicle);  // spot might already be taken
    }
    return spot;
}
This is just as broken as having no lock at all. The check (find spot) and the act (assign spot) must be inside the same lock acquisition. The whole point of locking is making the compound operation atomic.

Common Mistake #2: Using Different Lock Objects
Java
Bad Pattern
Copy
// BROKEN: different lock objects
private final Object lockA = new Object();
private final Object lockB = new Object();

public String enter(Vehicle vehicle) {
    String spot;
    synchronized (lockA) {
        spot = findAvailableSpot(vehicle.getType());
        if (spot == null) throw new ParkingFullException("No spots available");
    }
    synchronized (lockB) {  // different lock -- doesn't protect against lockA holders
        spots.put(spot, vehicle);
    }
    return spot;
}
All operations that maintain an invariant must be protected by the same lock. If enter() and exit() use different lock objects, they can run simultaneously, and the check-then-act race comes right back.

This bug is more subtle than it looks. Here is a real scenario where it bites:

Java
Copy
record Booking(String seatId, int priceMinor) {}

class TicketSystem {
    private Map<String, Booking> bookings = new HashMap<>();
    private int totalRevenueMinor = 0;

    // Developer thinks: "bookings and revenue are independent, use separate locks"
    private final Object bookingLock = new Object();
    private final Object revenueLock = new Object();

    public void book(String seatId, int priceMinor) {
        synchronized (bookingLock) {
            if (bookings.containsKey(seatId)) throw new AlreadyBookedException();
            bookings.put(seatId, new Booking(seatId, priceMinor));
        }
        // BUG: gap between locks -- another thread could cancel this booking here!
        synchronized (revenueLock) {
            totalRevenueMinor += priceMinor;
        }
    }

    public void cancel(String seatId) {
        Booking booking;
        synchronized (bookingLock) {
            booking = bookings.remove(seatId);
            if (booking == null) throw new IllegalArgumentException("unknown booking");
        }
        // BUG: if book() is between its two synchronized blocks,
        // revenue was not yet added, but cancel subtracts it
        synchronized (revenueLock) {
            totalRevenueMinor -= booking.priceMinor(); // half-applied state is observable
        }
    }

    static class AlreadyBookedException extends RuntimeException {}
}
If the map and revenue total form one in-memory aggregate, use one lock for both. If they live in durable storage, the equivalent boundary is a transaction or another storage-level atomicity protocol—not a JVM monitor around two database calls.

Java
Refactored
Copy
// FIXED: one lock protects the entire invariant
private final Object lock = new Object();

public void book(String seatId, int priceMinor) {

        if (bookings.containsKey(seatId)) throw new AlreadyBookedException();
        bookings.put(seatId, new Booking(seatId, priceMinor));

A Snapshot Is Not a Reservation
Java
Copy
// SAFE snapshot query; it does not reserve a spot
public int getAvailableCount() {
    int count;
    synchronized (this) {
        count = capacity - spots.size();
    }
    // The snapshot may become old immediately after the lock is released.
    log("Available spots at observation time: " + count);
    return count;
}
Releasing the lock before returning an immutable value is normal. No query can promise that the world will remain unchanged after it returns. The mistake is treating the count as a reservation and later acting on count > 0. Expose an atomic enter/reserve operation for that contract; keep getAvailableCount as an explicitly point-in-time observation.

When to Upgrade from Coarse-Grained to Fine-Grained
Coarse-grained locking is the right starting point. Here are the signals that you have outgrown it:

Signal	What is happening	What to consider
Measured wait time or queueing dominates latency	Threads spend significant time waiting	Reduce protected work or partition the lock
Read paths overlap long enough to contend	Readers serialize unnecessarily	Immutable snapshots, concurrent collections, or a read-write lock
Different operations touch different data	Unrelated operations serialize on the same lock	Per-resource locks
Operations are long-running	One slow operation blocks all others	Move I/O/callbacks outside the lock; reconsider the state boundary
Profiling shows lock contention as the bottleneck	Actual measured evidence, not speculation	Whatever reduces contention
The most important signal is the last one: measured evidence. Do not optimize for contention you have not measured. Premature fine-grained locking is a common source of deadlocks and bugs.

Read-Write Locks
Sometimes reads vastly outnumber writes. Consider a cache:

Java
Copy
class Cache<K, V> {
    private final Map<K, V> data = new HashMap<>();
    private final ReadWriteLock rwLock = new ReentrantReadWriteLock();

    public V get(K key) {
        rwLock.readLock().lock();
        try {
            return data.get(key);
        } finally {
            rwLock.readLock().unlock();
        }
    }

    public void put(K key, V value) {
        rwLock.writeLock().lock();
        try {
            data.put(key, value);
        } finally {
            rwLock.writeLock().unlock();
        }
    }
}
Multiple threads can hold the read lock simultaneously -- reads don't conflict with each other. But when a thread acquires the write lock, it has exclusive access -- all readers and other writers wait.

C++
Python
Copy
class Cache {
    std::unordered_map<std::string, std::string> data;
    mutable std::shared_mutex rw_mutex;

public:
    std::optional<std::string> get(const std::string& key) const {
        std::shared_lock lock(rw_mutex);  // shared (read) lock
        auto it = data.find(key);
        if (it == data.end()) return std::nullopt;
        return it->second;
    }

    void put(const std::string& key, const std::string& value) {
        std::unique_lock lock(rw_mutex);  // exclusive (write) lock
        data[key] = value;
    }
};
Read-Write Lock Semantics
The rules are simple:

Reader wants lock	Writer wants lock
No one holds lock	Granted immediately	Granted immediately
Readers hold lock	Granted immediately (shared)	Blocked until all readers finish
Writer holds lock	Blocked until writer finishes	Blocked until writer finishes
Multiple readers can hold the read lock at the same time, while a writer needs exclusive access. Admission policy is implementation- and mode-specific. In particular, Java's default non-fair ReentrantReadWriteLock does not promise FIFO admission and may indefinitely postpone readers or writers; fair mode trades throughput for an approximately arrival-ordered policy. Do not assume “a waiting writer always blocks new readers” without the chosen lock's contract. See the ReentrantReadWriteLock documentation.

Read-Write Lock: Full Example with Configuration Store
A configuration store can justify a read-write lock when reads overlap long enough to create measured mutex contention and a write must atomically replace or inspect several keys. For independent single-key operations, ConcurrentHashMap may be simpler; for a small configuration, publishing a new immutable snapshot can make reads lock-free.

Java
C++
Python
Copy
class ConfigurationStore {
    private final Map<String, String> config = new HashMap<>();
    private final ReadWriteLock rwLock = new ReentrantReadWriteLock();

    public String get(String key) {
        rwLock.readLock().lock();
        try {
            return config.get(key);
        } finally {
            rwLock.readLock().unlock();
        }
    }

    public Map<String, String> getAll() {
        rwLock.readLock().lock();
        try {
            return new HashMap<>(config);  // defensive copy
        } finally {
            rwLock.readLock().unlock();
        }
    }

    public void set(String key, String value) {
        rwLock.writeLock().lock();
        try {
            config.put(key, value);
        } finally {
            rwLock.writeLock().unlock();
        }
    }

    public void loadBulk(Map<String, String> newConfig) {
        rwLock.writeLock().lock();
        try {
            config.clear();
            config.putAll(newConfig);
        } finally {
            rwLock.writeLock().unlock();
        }
    }
}
With a regular mutex, overlapping reads serialize. With a read-write lock, the reads that are actually concurrent may proceed together; an arrival rate such as “1,000 reads/sec” does not mean 1,000 simultaneous readers. A writer waits for admitted readers and excludes new operations according to the lock's fairness policy.

When Read-Write Locks Are NOT Worth It
Use a read-write lock only when reads dominate and measurements show that allowing overlapping reads outweighs its extra bookkeeping and writer policy costs. There is no portable 10:1 ratio or microsecond cutoff. A plain mutex, an immutable snapshot, or a concurrent collection is often simpler; benchmark the actual critical section and workload before upgrading.

The Golden Rule
All accesses that participate in an invariant must follow one compatible synchronization protocol.

An invariant is a condition that must always be true. In the Parking Lot, the invariant is "each spot is assigned to at most one vehicle." Both enter() and exit() affect this invariant, so both must use the same lock.

If you add a getAvailableSpotCount() method and it reads the HashMap without synchronization while writers mutate it, the problem is more than ordinary business staleness: the access violates the map's concurrency contract and has no Java Memory Model visibility guarantee. Taking the same lock yields a consistent point-in-time snapshot, but it still cannot reserve future capacity.

Interview tip: When the interviewer asks "is this thread-safe?", walk through each method and check:

Does it read or write shared mutable state?
Do all accesses that participate in the invariant use the same synchronization protocol?
Then check what escapes the boundary: mutable references, callbacks, blocking I/O, lock ordering, process boundaries, and failure atomicity. A monitor proves only an in-process critical section whose callers obey the protocol.

Quick Recap
Coarse-grained locking means one lock protects all shared state in the object.
The check and the act must be inside the same lock acquisition -- never release the lock between them.
All accesses that participate in one invariant must use one compatible synchronization protocol.
Read-write locks can help measured read contention, but ratios and operation timings do not provide universal thresholds.
Coarse-grained locking is the right default. Only consider fine-grained locking when you can demonstrate that lock contention is actually a problem.
